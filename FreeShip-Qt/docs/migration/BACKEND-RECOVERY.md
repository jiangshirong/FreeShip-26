# 计算组件退出后恢复当前工作

2026-11-09。

计算组件退出或超时后，窗口原先只保留最后一幅画面，提示重新打开模型。
未保存修改虽然可能已有恢复副本，但直接重新打开原文件不包含这些修改。
从恢复列表选择当前船模时，还会弹出普通的保存确认；这时计算组件已经不可用，
默认的“保存”无法完成。此前担心的“选择恢复就删除副本”并非实际流程，
删除是在明确放弃并关闭或成功替换文档时执行，不能把两者混为一谈。

现在文件菜单增加“恢复当前工作”，只在有当前模型、计算组件已中断且没有正在执行的
操作时启用。中断提示说明入口和撤销历史边界。用户主动点击后重新建立计算会话：

- 优先按当前文档身份查找完整恢复副本。即使编辑已经提交、界面还没收到回复，
  也能找到比画面更新的副本，不依赖界面上一次记录的副本路径。
- 副本通过校验且版本不早于当前画面时，按原恢复流程加载；保持未保存，要求另存为。
  新会话建立自己的完整副本后，才删除旧副本。恢复失败继续保留原文件和画面。
- 如果没有副本，只能重新打开未修改文档的原文件，或者已有完整保存凭据证明属于
  当前修订的实际保存文件。重新读取前核对内容指纹，不能仅凭文件名或时间判断。
- 保存确认已完成但回复丢失时，恢复副本可能已经清理。此时按当前文档、修订、
  字节数、SHA-256 和实际文件核对已保存结果，恢复为已保存状态，不再次轮换备份。
- 副本过旧、损坏、被占用、缺失，或目标文件已改变时，拒绝替换当前画面并说明原因。
  不回退到较早原文件冒充成功，也不删除出错证据。较早副本仍可在重启后从列表选择。
- 在原来的恢复列表中领取当前中断文档，直接走上述版本校验，不再弹无法完成的
  普通保存确认。选择其他文档仍沿用原有未保存修改保护。

恢复后是新的文档会话，旧撤销链不恢复；之后的编辑、撤销、重做和保存照常工作。
新文件没有原路径时也可恢复。没有改动界面配色、原图标、几何算法或导出格式。

## 代码与验证

`src/app/model_session.cpp::resumeCurrent` 选择可验证的恢复来源，`recover` 检查当前
画面的版本下限；`startup.cpp` 和文件菜单接入实际动作。原恢复文件的格式与进程锁不变。

统一入口：`run_tests.py --suite qt-backend-recovery --runtime <运行包> --output <隔离目录>`，
支持 `--verify-deployment <正式目录>`。测试源码为 `qt_backend_recovery.py` 和
`qt/recovery_tests.cpp`，复用独立恢复文件解析器。

13 种会话场景真正终止测试自己创建的计算子进程，覆盖空闲时中断、第一次编辑及后续
编辑回复丢失、只读计算回复丢失、保存确认回复丢失、旧凭据，以及副本过旧、损坏、
占用、缺失和外部改写。检查恢复 FBM 字节、几何输出、未保存状态、后续编辑与撤销。
另在隐藏的正式窗口中通过动作绑定发现并触发“恢复当前工作”及恢复列表，核对普通、
未修改和新建船模的恢复、另存为及再次编辑。退出命令只属于明确启动的测试流程，
不提供给普通文档请求；它终止自己拥有的 QProcess，不按进程名称查杀程序。

第一次回归的四个失败是测试直接比较 Windows 混合分隔符路径造成的；
改用现有文件身份比较，保存位置要求未改变，原报告保留。
已有保存保护、恢复、会话及模型发布回归分别执行。输出在 C 盘
`FreeShip26-TestResults/backend-recovery-20261109`，交付回执位于
`FreeShip-Tests/maintenance/backend-recovery-delivery-20261109.json`。

只恢复最后成功持久化的模型，不恢复尚未提交的拖动、参数草稿、相机和旧撤销链。
实际桌面输入、全应用硬件断电和磁盘硬件故障不属于这些测试的通过结论。
