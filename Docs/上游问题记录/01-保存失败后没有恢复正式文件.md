# 保存失败后没有恢复正式文件

状态：已修复（Windows 文件故障回归通过，桌面操作未验收）。优先级：P1。

保存已有项目时，程序先删除旧备份，把正式文件改名为 `.Bak`，然后才序列化并写入新文件。中途失败没有恢复原文件的步骤，序列化本身还在后面的异常捕获范围之外。旧内容可能仍在备份里，但正式文件可能缺失或只写了一部分。

改法是先写同目录临时文件，确认完整后再替换正式文件，失败时保留原文件。这样保存出错后，不需要用户自己找备份恢复。

本地已有保存返回值判断，失败时不会再直接清除修改标志，但先改名、后写文件且不恢复的顺序仍在；本条只保留尚未解决的文件替换风险。

代码位置：`Units/FreeEdit.inc`，`TFreeEdit.File_Save`。见[上游保存顺序及异常处理](https://github.com/markmal/freeship-plus-in-lazarus/blob/1de17e99fb2b1cc559cdf27c5cafb595a627a641/Units/FreeEdit.inc#L6090-L6135)。

原始检查（修复前）：已核对源码，未做磁盘满、写入中断等桌面故障复现。修复时需检查：失败后原文件仍可打开，修改状态仍保留。

## 本项目修复（2026-10-30）

`File_Save` 现在先序列化，再通过 `Units/FreeSafeFile.pas` 的 `SaveProjectFile` 写入同目录独占临时文件。写完、刷新并关闭后才替换正式文件。旧文件先复制成完整 `.Bak`；任何前置步骤失败都不移动正式文件。序列化异常也纳入处理，失败不清除修改标志，并恢复保存前版本。

测试实际调用保存和另存为流程，覆盖序列化、部分写入、刷新、备份及替换失败、真实 Windows 文件占用、新文件失败，以及中俄文件名、FBM/FTM 正常往返。见[保存报告](../../../FreeShip-Tests/reports/save-safety-ftm-final-20261030/report.json)和[第一批修复记录](第一批修复-文件安全.md)。

备份已更新、正式替换失败时，`.Bak` 是原正式文件的完整副本，更早的备份不再保留。未做断电、网络盘、POSIX 和 ACL 继承验收。本次为本地修改，尚未创建 Git 提交。
